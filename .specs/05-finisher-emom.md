# Spec 05: EMOM finishers (build-plan item I)

## Objective
Generate and surface the per-day EMOM finisher block (defined in `docs/program/phase1-warmup-finisher-source.yaml`, currently unread by any code) on the session response, including D6's jump-rope duration→rope-weight progression — closing the same `GenerateResponse.scope` gap Spec 04 addresses for ramp sets.

## Background / design decision
Finishers are NOT `Tier`/`TierExercise` slots (they're one fixed block per day, outside the giant-set/anchor structure) and nothing in the schema currently models them. Two options exist; **this spec picks modeling finishers as first-class `Movement` + `MovementState` rows**, reusing the whole progression engine (day-scoping via `MovementState.day_id`, ladder-stepping via `advance.py`) instead of building a parallel state system for the one day (D6) that actually needs progression:

- One `Movement` row per day's finisher exercise (`kb_swing_finisher_d1`, `sled_push_finisher_d2`, `sandbag_finisher_d4`, `farmer_carry_finisher_d5`, `jump_rope_finisher_d6`), `lift_category=LiftCategory.NONE`, `progression_mode=ProgressionMode.CONDITIONING` for the four fixed (non-progressing) days, and a **new** `ProgressionMode.FINISHER_LADDER` for D6 only.
- A new small table `DayFinisher(id, program_day_id FK, movement_id FK, duration_minutes, param_json)` — `param_json` holds the day-specific EMOM parameters as-is from the yaml (`weight_lb`/`resistance_level`/`target_reps_per_minute`/`work_seconds_per_minute`/`equipment`, whichever apply to that day) rather than forcing every finisher's disparate parameter shapes into dedicated columns.
- D6's progression state lives on `MovementState` via two **new additive columns**: `duration_ladder: Optional[list]` (JSON, mirrors the existing `rep_ladder`/`position_ladder` pattern on `Movement`, but this one is genuinely per-athlete progressing *state* so it belongs on `MovementState` alongside `current_duration_seconds: Optional[int]` and `current_rope: Optional[str]` — the ladder-of-ropes itself, `rope_ladder`, is static config and belongs on `Movement` next to the movement's other ladder fields).
- A **new** `ProgressionRule` dispatch entry in `ironlog/engine/advance.py`: `FINISHER_DURATION_THEN_ROPE` — steps `duration_ladder` via the existing `_ladder_step` primitive (advance.py:160-178) exactly like `_incline_reduction`/`_rep_ladder`; on reaching the duration ladder's terminal rung, instead of holding, swap `current_rope` to the next `rope_ladder` entry and reset `current_duration_seconds` to the ladder's first rung. This is new logic (no existing rule does "exhaust A → reset A, advance B") — model it as a fourth `_DISPATCH` function following the shape of `_assistance_reduction` (advance.py:187-194), not by extending an existing function.

## Edge cases
- **Rest days (D3, D7)**: no `DayFinisher` row → no finisher block on the response (not an empty/null placeholder that looks like an error — omit the field or make it explicitly `None`, whichever the DTO shape settles on).
- **D6 terminal state**: at `current_rope="one_lb"` (last rung) AND `current_duration_seconds=50` (last rung), the advance function must HOLD (no further progression) rather than index past the ladder — mirror the existing terminal-rung hold behavior in `_ladder_step`.
- **Meso/day structure changes**: if a day's `Tier`/anchor structure changes (e.g. a meso swap), the finisher is independent of tier structure and must NOT be affected — verify `DayFinisher` lookup keys only off `program_day_id`, never off tier/slot IDs.
- **Fixture-impact check** (per CLAUDE.md's spec-format requirement): any existing test that asserts on `GenerateResponse.scope`'s literal text, or on the full shape of a generated session response, will need updating once the finisher field is added — grep `tests/` for `scope` and `GenerateResponse` before merging and update accordingly; this is in-scope for this spec, not a follow-up.
