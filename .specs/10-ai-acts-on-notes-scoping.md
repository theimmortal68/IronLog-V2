# Scoping Doc 10: "H — AI acts on programming notes" (NOT an implementation spec)

**This is deliberately not a directly-dispatchable spec.** The build-plan marks this item "own design, large" — writing a full implementation spec now would mean inventing safety-critical design decisions (which actions, if any, an AI may take without per-instance human confirmation) without the brainstorming pass this kind of feature needs. This doc captures what's already true in the codebase and the concrete open questions a real design session needs to resolve before any spec/dispatch work starts.

## What already exists (confirmed 2026-07-10/11)

- **Classification already works and is in production.** `ironlog/notes/classify.py`'s `NoteClassifier` (Gemini-backed) classifies every captured note into one of 4 classes (`CONFIG_CHANGE`, `PROGRAMMING_REQUEST`, `TRANSIENT_FLAG`, `JOURNAL`) and, for `CONFIG_CHANGE`, extracts a `proposed_change` (movement/action/params) plus an `action_type` (`SWAP`, `LOAD_INCREASE`, `LOAD_DECREASE`, `REP_CHANGE`, `OTHER`).
- **Applying a note is currently a manual, human-confirmed action.** `ironlog/notes/apply.py`'s `apply_override` takes an EXPLICIT `tier_exercise_id` the caller (the app's Review screen, via a slot picker) has already resolved and confirmed — it deliberately does NOT auto-infer the slot from the note's classification. This is a real, working safety property: the classification's `proposed_change.movement` (the SUBJECT) can differ from the note's `movement_id`/`session_id` (the ATTACHMENT — where the athlete happened to be logging when they wrote it), and this session's own work (2026-07-10) hit exactly that gap live: a Day-5 Hip Thrust note attached to a Day-2 session correctly required the athlete to pick "D5 Lower B" explicitly via "Change slot" rather than the app guessing.
- **The load-safety-clamp incident is directly relevant precedent.** Applying a flat "+5lbs" note to Hip Thrust this session broke `/generate` (exceeded the engine's 225lb bottom-position clamp) — caught only because a human (Tier A) was investigating in real time and could revert. An AI empowered to apply notes autonomously would need to either (a) always run the same validator/clamp checks BEFORE committing an override (the engine has this logic; it's not currently in the note-apply path at all, only surfaced retroactively via a failed `/generate` call), or (b) never auto-apply LOAD-type changes to clamp-bounded movements (HT) without a human checking the result. This is exactly the kind of "hard rules = code filter, NOT prompt/LLM judgment" boundary already established as a principle for a related deviation-handling feature in this project's history — it applies here too.
- **"Reorder" has no structured category today.** The one reorder request seen this session (note #7, "move knee raises between meadows rows and single arm rows") was classified `action_type=OTHER` (the classifier's catch-all) with a `proposed_change.action` string of "Add weight and reorder sequence" — i.e., a compound request the current 5-way `action_type` enum has no dedicated slot for, and the reorder itself was applied via a hand-written one-off migration script (`d4_reorder_knee_raise.py`), not any note-apply code path at all.

## The three named categories from the build-plan, mapped to reality

| Build-plan category | Current state |
|---|---|
| **Reorder** | No structured classification, no apply mechanism at all. Every reorder so far has been a hand-written one-off script. |
| **Assist+reps** | Partially covered: `REP_CHANGE` and `LOAD_INCREASE`/`LOAD_DECREASE` action_types exist and the manual apply path (`apply_override` with `OverrideType.REPS`/`LOAD`) already works for these — confirmed working this session (Meadows Row +1.25lbs, applied manually after human review). What's missing is autonomous application without a human in the loop. |
| **Cross-day requests** | The attachment-vs-subject gap is understood and the CURRENT design's answer is "require the human to pick the right slot explicitly" — which is a deliberate safety choice, not a gap to code around. An "AI acts autonomously" version would need its own resolution strategy for which day/slot a note actually means, and get it right without human confirmation — a materially harder, higher-stakes version of a problem the current design already solved by NOT trying to guess. |

## Open questions a real design/brainstorming session needs to answer

1. **What, if anything, should ever apply without per-instance human confirmation?** Given tonight's clamp-violation near-miss happened with a HUMAN reviewing in real time, the bar for autonomous application should be treated as genuinely high, not assumed. Candidate framing: maybe nothing applies autonomously, and "AI acts on notes" really means "the AI proposes a fully-resolved, safety-checked action for one-tap human confirmation" — a UX/trust improvement over today's picker-based flow, not true autonomy. This is the single most important question and should be resolved first; it determines whether this is a small UX feature or a genuinely high-stakes autonomous-agent feature.
2. **What does "reorder" as a structured, applicable action_type even look like?** Needs its own classification category, its own override/application mechanism (today's `SlotMovementOverride` model has `MOVEMENT`/`LOAD`/`REPS` override types — reordering `TierExercise.exercise_order` is a different kind of change entirely, more like the ad-hoc migration scripts written this session than a slot override).
3. **How does a cross-day request get resolved safely** if the design goal is to reduce (not just preserve) the human-confirmation step? What's the actual failure cost of a wrong auto-resolution vs. today's explicit-picker safety net?
4. **Does applying a LOAD/REPS change need the engine's validator run BEFORE commit**, not just discovered after a broken `/generate` call? (Almost certainly yes, regardless of how the other questions resolve — this is a real gap in the CURRENT manual-apply path too, worth fixing independently of the "AI acts autonomously" question.)
5. **Reversibility and audit**: today's overrides are already revertible (`/overrides/{id}/revert`, confirmed working this session) and carry `source_note_id` provenance. Does an autonomous-action version need anything beyond what already exists, or does it inherit these properties for free?

## Recommendation
Before writing an implementation spec for this: (a) resolve question 1 above — it changes the shape of everything else — via a real brainstorming session (per this repo's own established convention for exactly this class of decision), not an inline judgment call; (b) consider fixing question 4 (pre-commit validator check on note-apply) as its own small, independent, immediately-actionable spec regardless of how H's larger design lands, since it's a real safety gap discovered this session and doesn't require resolving the autonomy question first.
