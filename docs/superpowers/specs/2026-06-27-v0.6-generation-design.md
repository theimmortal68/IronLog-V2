# IronLog-V2 v0.6 — Generation Loop Design

**Status:** design closed, awaiting spec-review gate → writing-plans
**Parent spec:** `docs/06_generation_algorithm_spec.md` (the generation algorithm; this doc *resolves* its open decisions into a buildable design)
**Date:** 2026-06-27
**Scope:** the between-session generation loop — the first non-deterministic piece (LLM re-enters the engine at runtime as the session-proposer). Build-and-test-only; prod reseed and runtime-key provisioning are separate user-owned steps (see §10).

---

## 0. What this is

docs/06 describes the generation algorithm but leaves several decisions to interpretation (most visibly: §1/§5 say the model "never invents numbers" while §3-step-4 says it "emits a complete Session"). This design closes every such decision through seven foundational forks plus a beta-depth refinement tier, so the build runs against a spec with **zero open decisions** (the discipline that makes a long, clean, unsupervised build possible).

The whole loop, composed:

> **selections-only contract → deterministic-context single call → feasibility-filtered / judgment-soft-presented menu → outcome-only repair + two-tier fallback → analyze-at-log / generate-on-request loop (two-writer boundary) → deterministic-glue assembler → approval gate with commit-at-approve.**

Every seam resolves on the same two principles: **rope where there's judgment, rules where there's a right answer**, with the deterministic validator as the construction-level guarantee throughout.

---

## 1. Principle ledger (threaded through every fork)

These are the reusable principles the design rests on. Each fork cites the one(s) it applies.

1. **The selections/numbers line (Fork 1).** Constrain what has a right answer (numbers), free what requires judgment (selections). The model proposes *what to do*; the engine computes *the numbers*.
2. **Principle-language governs mechanism-language (Forks 1, 2).** docs/06's *principles* (auditable, deterministic, rules-dispose) are authoritative; its *process descriptions* ("emits a complete Session", "calling functions") are implementation sketches the principles constrain. "Complete Session" = the assembled artifact; "calling functions" = the engine calls them.
3. **Guarantee outcomes, don't dictate methods (Forks 3, 4).** The validator guarantees the *outcome* (a requirement is met) by rejecting any session where it isn't. Anything *beyond* the validator that constrains *how* the outcome is reached is judgment-stripping, not safety.
4. **The validator is the construction-level guarantee (Forks 3, 4, 7).** "The requirement is met" is true by construction *because the validator disposes of any session that fails it* — that is the dispose half of rules-dispose/model-proposes. So no second enforcement point is needed.
5. **Single source of truth (Forks 3, 6).** Never encode the same invariant in two places (they drift). The validator is the sole requirement-enforcer; the calibration block is the sole fresh-movement-load resolver; the assembler routes, it does not duplicate.

## 2. Architecture overview

The pipeline (docs/06 §3), with forks resolved and ownership marked **[D]**eterministic / **[L]**LM:

```
LOG (client posts completed session)
  └─> run_analysis(session_id, db, week_keyer)        [D]  analyze→apply: e1rm/history/calibration_status/counters
                                                            (idempotent, keyed by session_id — §Fork5)

REQUEST (client asks for next workout)
  1. RESOLVE CONTEXT                                   [D]  engine calls getMovementState/getWeeklyLedger/
                                                            getManifest/getRecentSignatures; loads the PROGRAM prior;
                                                            computes owed reqs; builds per-slot menus
                                                            (= program-anchor + feasible alternatives)
  2. LAY FIXED SKELETON                                [D]  T1 anchors + meso-rotation variant; knee slots (Fork 3)
  2b. CONDITIONAL GATE (§3A)                           [D]  any slot carry a feedback/novelty/weak-point signal?
       └─ NO  → emit the PROGRAM deterministically (no LLM call) ─────────────────┐
       └─ YES → proceed to 3                                                       │
  3. BUILD PROMPT (inject 1+2 + program prior + soft) [D]  single prompt; the logged replayability artifact
  4. PROPOSE                                           [L]  one call → selections JSON (keep-program | justified delta)
                                                            (movement_id, order, variant, tags, rationale) — NO numbers
  5. ASSEMBLE  ◄──────────────────────────────────────────(deterministic-emit path joins here)──┘
                                                       [D]  glue: route each movement through existing progression/
                                                            PhasePolicy/calibration → full Session w/ all numbers
                                                            (computes prospective current_load; does NOT write it yet)
  6. VALIDATE                                          [D]  clamp computed numbers over caps; reject structural/
                                                            requirement misses with outcome-only structured reasons
       └─ reject → repair: back to 4 (whole-session re-propose), bounded 3 retries
       └─ 3 failures → TWO-TIER FALLBACK              [D]  last-valid-refreshed | cold-start = emit PROGRAM (logged)
  7. APPROVE                                           [human / auto-approve-clean]
       └─ on approve: COMMIT → write current_load + persist PLANNED session   [D]
```

The LLM touches **at most one box** (step 4) — and only when the conditional gate (2b, §3A) fires; on a quiet week it is never called and the program is emitted deterministically. When called, it is a single deterministic-context-in / selections-out call. Everything else is deterministic and testable in isolation by stubbing the proposer port with fixed selections.

## 3. The foundational forks (1–7) — settled permanently

> All of §3 is **foundational-locked**: these define the loop's shape and are not beta-provisional. Changing any would change what the system *is*.

### Fork 1 — Proposal contract: selections-only
**Decision.** The LLM emits only the adaptive-layer **selections**: per adaptive slot, a `movement_id`, plus session-level `ordering`, per-movement `variant` choice, `technique tags`, and a free-text `rationale`. **No loads, no schemes, no reps, no RPE.** The deterministic assembler computes every number and assembles the `Session`; the validator confirms structure/feasibility.
**Schema-constrained by construction (strengthening).** The output is enforced at the API layer via Gemini structured output (`response_mime_type: "application/json"` + `response_json_schema` over the selections contract — §6). "No numeric fields" is therefore guaranteed by the *response schema itself*, not merely by prompt instruction: the model physically cannot emit a load/rep/RPE field because the schema has none. Selections-only AND schema-validated by construction. (Menu-membership — `movement_id` ∈ the slot's candidate menu — remains a deterministic post-check per Fork 3, since the schema constrains shape, not value-membership.)
**Rationale.** Makes "never invents numbers" true *by construction* (no number field exists to leak) — the strongest form of rules-dispose. Smallest, cheapest, most-robust output. Makes the two-writer boundary provably safe: `current_load` is a deterministic derivation from the selections, never an LLM value. Reconciles docs/06 §3 ("complete Session" = the assembled artifact) with §1/§5 (the governing "never invents numbers"). *(Principles 1, 2.)*
**Rejected.** Full-session-with-numbers + validator-clamp (numbers redundant-or-clamped, never better-than-deterministic; adds a clamp-bug leak path; weakens the guarantee from construction to vigilance). Selections + numeric "hints" (unbounded advisory channel the validator can't check; genuine load nuance belongs as a deterministic rule like the library's `start_ratio`).

### Fork 2 — Invocation: deterministic context-injection, single call
**Decision.** The **engine** runs RESOLVE CONTEXT itself (calls `getMovementState`/`getWeeklyLedger`/`getManifest`/`getRecentSignatures`, computes owed requirements, builds the candidate menu), packs all of it into **one prompt**, and the LLM returns selections in a single shot. The model is grounded by *injection*, not autonomous fetching.
**Refined by the evolving-seed model (§3A).** The injected context now also carries, per slot, **the program's prescribed movement as the prior/default**. And the call is **conditional** (§3A): the LLM is invoked only when ≥1 slot carries a feedback signal that could justify a deviation; on a quiet week the engine emits the program deterministically and the LLM is never called.
**Rationale.** Deterministic and **replayable** — the single logged prompt *is* the §10 auditability artifact (vs an un-replayable tool-call trajectory). One round-trip: fast, cacheable. **Eliminates the tool-loop-exhaustion failure mode** observed repeatedly in this environment (local-model agentic loops: 50–60% zero-output; opencode orphan-process leaks). Keeps the model on an engine-controlled information diet (the guardrail). "Calling functions" (§1) is honored by the engine making the calls. *(Principles 2, 4.)*
**Rejected.** Tool-calling agent (reintroduces the demonstrated tool-loop unreliability + nondeterminism + un-replayable trajectory; "more rope" over the information diet with no selection-quality payoff — the engine already knows what context a selection needs). Hybrid with a few optional lookup tools (side-door loop liability; if a specific lookup proves genuinely needed, add it as a deterministic context-resolution step, not a live model-driven tool).

### Fork 3 — Candidate menu: program-anchored, feasibility hard-filtered, judgment soft-presented
**Decision.** Per adaptive slot, the engine builds the menu by:
- **Anchoring on the program (the evolving-seed prior, §3A):** the slot's menu is **`[the program's prescribed movement] (the anchor/default) + feasible alternatives`** — not an open feasibility menu. The LLM decides whether to *keep the program default or deviate to an alternative, justified by feedback*, never picks from scratch. Default-to-program when nothing justifies a change (so meso 1 / quiet weeks emit the program as written — this dissolves cold-start).
- **Hard-excluding** from the alternatives anything a wrong pick makes structurally impossible or guaranteed-reject: not `ACTIVE`; not equipment-feasible in the active-phase manifest; not matching the slot's tier + pattern. The menu is **guardrail-by-construction** — the model cannot pick an infeasible or wrong-pattern movement.
- **Soft-presenting** (as context the model weighs, not pre-constrained): owed-requirement flags, recent signatures (for soft novelty, §7), and the deterministic `detect_stall` signal + limiter hint (weak-point, §9).

The validator then **hard-rejects** unmet requirements / feasibility and **soft-checks** novelty (relaxable — §7 priority order preserved).

**Owed-requirements sub-decision: soft-present + validator-enforce (NOT menu-force).** Three-way split:
- **Structure is deterministic** — the DayTemplate creates the slot (a knee slot exists regardless of the model).
- **The fill is the model's** — *which* owed-modality movement (which Nordic variant) and *where* it sits (ordering for the transition budget) is judgment.
- **The requirement is validator-enforced** — if a requirement is unmet, the validator rejects → repair.

**Rationale.** Keeps the model's judgment *meaningful* (the whole point of an LLM here) and *bounded* (the impossible is un-pickable). Hard-forcing owed movements adds no safety the validator doesn't already provide (Principle 4) while stripping the variant/ordering judgment §7/§9 grant, and it duplicates the requirement logic across menu+validator (violating Principle 5). Repair loops stay rare *because* feasibility is hard-filtered — the menu can't yield infeasible picks, so the only rejects are genuine "you owed a row and didn't place one" judgment failures, which *should* repair. *(Principles 3, 4, 5.)*
**Rejected.** Narrow menu / pre-constrain everything (collapses judgment to near-nothing → self-refuting "the LLM shouldn't be here"; hard-codes novelty against §7's soft priority). Wide menu / full library + validator-rejects (model re-derives feasibility the engine knows cheaply — the Fork-2 anti-pattern; more repair loops).

### Fork 4 — Repair loop: outcome-only rejection, whole-session re-proposal, two-tier fallback
**4a — Rejection contract: strictly outcome-only.** The structured reason states the violated requirement, its status, and its **locus** (naming the slot is *fact* — part of the constraint's identity — not a fix), but never the remedy. Test: *does the rejection state a fact the validator knows, or a decision the model should make?* Facts only. ("Knee slot unfilled — Nordic owed 1 unmet" ✓; "add Nordic Curl to slot 3" ✗.)
*Rationale:* outcome/method line applied to the feedback channel (Principle 3). A directive rejection relocates Fork-3's rejected hard-force into the repair path (the validator computing the fix ⇒ the selection was deterministic ⇒ the LLM was never needed) and hides model-competence failures. Faster convergence is not worth laundering validator decisions through the model; convergence is already bounded (3 → fallback).
**4b — Repair scope: whole-session re-proposal.** The model re-emits all selections given its prior attempt + the rejection. Cross-slot constraints (pull:push ratio, novelty signature) are **structurally un-fixable** by slot-local repair (the best fix for a pull:push shortfall may be a slot the validator didn't flag). Partial repair isn't just riskier — it's *incapable* of the cross-slot case, which is exactly what repair most needs.
**4c — Two-tier fallback** (after 3 retries, or offline): the engine self-produces a guaranteed-valid session.
- If a prior valid session for this `day_role` exists → **replay it with loads refreshed** from current `MovementState`.
- If none exists (cold-start / new day_role) → **deterministic skeleton-fill**: anchors + each adaptive slot filled with a deterministic candidate from its menu (semi-anchor held movement; else a sensible per-pattern default — see beta flag in §5).
- Either tier is **logged as a fallback** (§10).
*Rationale:* the loop cannot close if generation can ever produce nothing (§8/§10 "degrades to a repeat, not a failure"). *Beta-critical — see §5.*

### Fork 5 — Post-session loop: analyze-at-log / generate-on-request
**5a — Trigger (decision).** Two decoupled endpoints: **LOG → `run_analysis` fires immediately**; **next-session REQUEST → generation fires** (when the user is about to train).
*Rationale:* freshest-state generation is a **correctness property** — generation always reads everything known up to the instant of training; no stale pre-generation window (rejected B: pre-generate-on-chain), no deferred-analysis ordering-blur (rejected C: all-on-request). Maps to the natural rhythm (analyze on finish, generate when ready).
**5b — Ordering (automatic).** `run_analysis` must complete before generation (generation reads post-analysis `MovementState`). Under 5a this is *structurally* true (analyze-at-log finishes long before a later generate-on-request) — free, not enforced.
**5c — `current_load` write (two-writer boundary, concrete).** `run_analysis` writes the **outcome** fields (e1rm, e1rmhistory, calibration_status, counters) at log. Generation is the **sole writer of `current_load`**, computed by the assembler from post-analysis state — but the *write commits at approve* (Fork 7c), not at assemble. The two writers touch **disjoint fields at disjoint times** → boundary safe by construction *and* by non-simultaneity.
**5d — Idempotency (asymmetric — this is the point).**
- **Analysis idempotency: keyed by `session_id`, no-op on re-log. Beta-critical and must be CORRECT.** A duplicate `e1rmhistory` row does not error — it silently doubles the data the analyzers read (stall/calibration), producing a wrong conclusion. This is the silent-wrong-data class; do not defer or half-build it. *See §5 flag.*
- **Generation idempotency: free under 5a + 7c.** Commit-at-approve means a discarded regenerate writes **nothing** (not "writes-then-overwrites-to-same-value" — genuinely never wrote). A regenerate that re-selects a *different* free movement just produces a different *unapproved* candidate; unapproved candidates touch no state.

### Fork 6 — The deterministic assembler (glue, not new math)
**Decision.** The assembler is **orchestration over existing engine logic**, the "six specs, one runtime" convergence point. Per prescribed movement (anchors + selected): scheme→set/rep from the library `scheme` + PhasePolicy; load from the progression model applied to post-analysis `MovementState`; reps/RPE from the phase band. Flow: selections → assemble → validate → emit. It calls already-tested progression/PhasePolicy/calibration/Session-PlannedSet logic; it does not reinvent it.
**Pin 1 — fresh-movement load routes to the existing resolver.** A fresh free-tier movement (no prior `current_load`) gets its start from the **existing calibration path**, resolved by reading the movement's library fields (`calibration_status` / `start_ratio` / `load_floor`) and dispatching to the existing resolver (`CALIBRATING` at `load_floor`; ratio-variant at `anchor_e1rm × start_ratio` — the e1RM-only-ratio principle). The assembler **must not** contain its own fresh-movement branch (Principle 5 — "what load does a fresh movement start at" lives in one place).
**Pin 2 — commit point: resolved in Fork 7c (commit-at-approve).** The assembler *computes* the prospective `current_load`; it does not write it.
**`current_load` write scope.** Uniform: every prescribed movement (anchor, semi-anchor, free) gets its `current_load` written **at approve** — simplest rule; gives any future re-selection of a free movement a reference; harmless for movements that don't repeat (and write-free until approve, so discarded candidates strew nothing).

### Fork 7 — Approval gate (posture locked §174) + commit-at-approve
**7a — "Clean" = zero repairs AND zero clamps → auto-approved.** A session that needed a repair (validator rejected → re-propose) or a clamp (a computed number hit a cap) is surfaced for human approval. Strict → relaxes once trusted.
**7b — Fallback never auto-approves — as a *derived* property of 7a.** A Fork-4c fallback is by definition not-clean (it took the maximum repairs), so 7a automatically surfaces it. The most important case to see (model failed 3×, engine substituted) is caught by the general rule, not a special-case check that could be forgotten.
**7c — Commit point: commit-at-approve.** The write of `current_load` to `MovementState` (and persistence of the PLANNED session as committed) happens at the approval moment — human-approve (first meso / surfaced sessions) or auto-approve-clean (the auto-approval *is* the commit). `current_load` thus means exactly "the committed next prescription" — the write happens at the moment the value *becomes true*. Discarded regenerates are **write-free by construction**; the free-movement re-selection problem *ceases to exist* (unapproved candidates touch nothing) rather than being guarded against. *(Principles 1, 4.)*
**7d — Full provenance logging (§10).** Every generation logs: injected prompt + selections + clamps + repairs (with rejection reasons) + approval-mode (human/auto) + commit + fallback-if-used. Auto-approved-clean sessions are fully logged → post-hoc auditable even when no human saw them live.
**7e — No in-session editing for beta.** The beta interaction is **approve or regenerate** (or drop a note that feeds the *next* generation). In-session hand-editing would reopen the "human sets a number" hole Fork 1 closed — the determinism guarantee exists so numbers are always engine-computed; a human override punches the same hole the LLM would. In-session editing is a genuine (hard) post-beta question.

## 3A. The evolving-seed model + scope boundary (refines Forks 2/3; foundational-locked)

The user's program (the full Phase 1 prescription) is **the initial state of an evolving prescription, not a fixed-forever script and not raw material the LLM freely regenerates.** Meso 1 *is* the program followed as written; over time the LLM proposes **evidence-justified deltas** from it (a stalled accessory swapped, a weak-point-biased selection, novelty introduced where the program would otherwise repeat). The program is the **prior**; LLM adaptations are deltas from it, each a feedback-justified hypothesis measured against the program baseline.

This dissolves cold-start: there is no skeleton-fill weirdness because the cold-start default **is the program** (a real designed session). The Fork-4c cold-start fallback becomes "emit the program as written," and the "trainable-not-optimal" concern for skeleton-fill is moot.

### Conditional LLM invocation (the gate — pinned + testable)

The LLM is invoked **iff ≥1 main-work slot carries a feedback signal that could justify a deviation.** Otherwise the engine emits the program deterministically and **the LLM is never called.** This is latitude-gated-**by-construction** (Principle 4): on a quiet week the model *cannot* deviate because it isn't asked — not "we trust it to return the defaults."

**A "feedback signal that could justify a deviation" is, for a slot, ANY of:**
- the slot's movement has a fired `detect_stall` signal (`StallSignal.stalled`), OR
- a weak-point limiter is present for it (from the survey / stall hint), OR
- novelty is owed (the candidate signature would repeat — ≥30% similarity to the last 2 same-`day_role` sessions, §7), OR
- an open `Note` / RPE-trend flag targets it.

If **any** slot qualifies → the LLM is called **for the whole session** (Fork 4b whole-session reasoning). If **none** → deterministic program emission, no LLM call. Meso 1 has no history → no signals → provably deterministic.

### Scope boundary (what v0.6 does and does not do)

| Program element | v0.6 treatment |
|---|---|
| Adaptive **main-work** slots (giant-set / accessory) | **LLM evolves** — program movement is the anchor; feedback-justified deltas. *This is the generation loop.* |
| **T1 anchors** + **meso rotation** (which variant this meso) | **Deterministic from the seed** — read the meso, place the variant. No LLM. |
| **HT 220 cap**; **RPE caps** | **Map to existing mechanisms** — validator `ht_bottom_clamp = 220` ✓; `phase_hard_cap` / PhasePolicy ✓. |
| **Loads** | **MovementState** (`current_load`), two-writer boundary unchanged. |
| **Warmups, finishers (EMOM + power-slot rotation), Z2** | **DEFERRED to v0.7** ("full program"). They are *fixed scaffolding the LLM never evolves*; not part of the generation loop. Beta emits **main-work only**, with an honest in-app marker: "warmups / finishers / Z2 per the program doc — not yet in-app." |
| **Richer per-exercise progression rules** (single-session, rep-ladder, rep-at-cap, band-reduction, tube-reduction) | **OUT of v0.6 scope — they belong to the analysis/apply layer that *advances state*, NOT generation.** Generation **only reads `current_load`**; it never computes progression. Today's engine does double-progression; the program's other rules are a future analysis-layer concern, and **generation is unaffected** because it reads whatever load-state holds. *(This line prevents anyone later putting progression logic in the generation loop.)* |

The boundary keeps v0.6 = **the generation loop that evolves the main-work program from feedback**. The fixed scaffolding (v0.7) and the progression-rule richness (analysis layer) are cleanly assigned elsewhere.

### Requirement-enforcement SCOPE split (pins Fork 3's "validator-enforce" — surfaced by the Task-7 gate)

Fork 3 said "owed-requirements = soft-present + **validator-enforce**", and the build revealed "validator-enforce" silently conflated two scopes. A weekly requirement is **categorically not a per-session property** — no single session can satisfy "knee 2×/week", and a non-knee day (D1) has no knee work *by design*, so enforcing a weekly target per-session is a **category error** that makes every non-knee day un-generatable. Apply each rule **at its correct scope**:

- **Per-session structural requirements → validator HARD-enforces at generation** (always-on, NOT `tallies`-gated): primaries-first, giant-set 3×3, giant-set concurrency ≤3, single-KB, equipment-in-manifest, HT bottom-clamp, load floor/cap, RPE cap, **and menu-membership — every selection ∈ its slot's candidate menu** (which, because a knee slot's menu is knee-modality-only and tier/pattern-filtered, *hard-guarantees* "the knee slot on a knee-day is filled with a knee movement", and every slot's tier/pattern correctness). These are genuine per-session properties; the per-session validator is their right enforcer.
- **Weekly aggregate requirements → program-design gating + ledger soft-biasing, NOT a per-session reject:** knee frequency (2×/wk etc.) and pull:push ratio are guaranteed **construction-level** at seed time (Task 2's `test_knee_frequencies_are_satisfiable` — the program literally can't seed without satisfying them) and **soft-biased** across the week via owed-requirements (Fork 3 nudging). A week generated from a frequency-satisfying program is frequency-satisfying *by construction*; per-session re-checking would be a weaker, redundant, over-rejecting vigilance check. So `build_validation_context` passes `tallies=None` (skips `KNEE_FREQUENCY`/`PULL_PUSH_RATIO`), and per-session validate stays structural.

This is the same class of fix as the Task-2 guard-bypass: the rule was right in intent but scope-ambiguous; pin the scope so "validator-enforce" can never again be read as "enforce weekly rules per-session."

## 4. Refinement tier — settled for beta (swappable / good-enough)

> All of §4 is **beta-depth**: deliberately not fully resolved, because each item is either swappable by construction, dormant until data accrues, or mechanical. Over-resolving them now is designing against data that doesn't exist yet.

### 4.1 Runtime model + prompt — the proposer port [beta-depth, swappable]
- **The generation LLM sits behind a swappable client port:** `propose_selections(context) -> Selections`. Forks 1–2 made this possible (single structured call, no tool loop), so the model is a config concern, not an architectural one.
- **Beta adapter: `gemini-3.1-flash-lite` via the AI Studio free tier — HTTP call from the Python server** to the Gemini API endpoint (NOT a CLI subprocess). Chosen because it is **the task-matched model**: Google identifies Flash-Lite as the canonical choice for classification / routing / structured-extraction, which is exactly our bounded selection-from-a-filtered-menu task (not long-form reasoning). **Zero cost, zero billing** (API key from AI Studio + a Google account, no credit card); comfortably inside the free limits at our volume — ~5–15 calls/day against a 1,500 RPD cap (~1%), 15 RPM never approached (a ~4k-token call, bursts of ≤~15 with reading-time between regenerates); data-training term accepted as immaterial for workout data.
- **Call configuration:** **structured output** — `response_mime_type: "application/json"` + `response_json_schema` built from the selections contract (§6), so the output is schema-constrained by construction (the Fork-1 strengthening). **Thinking low/off** for beta (bounded selection doesn't need extended reasoning; revisit if quality needs it). **Function calling deliberately unused** — Fork 2 is context-injection single-call, not an agentic loop; no tools are exposed to the model.
- **Swappable in one line (Forks 1–2):** **up to a stronger non-lite Flash** — `gemini-3.5-flash` (newest), `gemini-3-flash-preview`, or the floating alias `gemini-flash-latest` (a one-line model-string change) if beta shows weak selection quality — let real use decide rather than pre-paying for the stronger model; or to a **paid tier**; or to the **local llama-server (Qwen3.5-35B)** as the post-beta privacy/cost optimization once the loop is validated (the single-call selections-out task is within a 35B's capability — the failure mode was the *agentic loop*, eliminated by Fork 2). Beta launches on the task-matched Flash-Lite; escalate only if selection quality warrants.
- **Prompt template (first draft, beta-depth):** injected context = skeleton + per-slot feasibility-filtered candidate menus + owed-requirement flags + recent signatures + weak-point hint + open notes; output contract = the selections JSON (§6). **Prompt-tuning happens against real sessions post-beta** — do not over-invest pre-launch.
- **⚠ Provisioning prerequisite (user-owned, see §10):** the runtime path is **not yet provisioned** — no Gemini API key on myflix, no HTTP-client/SDK wired. Wiring it needs an AI Studio API key (a secret, but **free — no billing/card**) reachable by `ironlogv2.service` + an HTTP client (`httpx` or the `google-genai` SDK) in the venv. The build delivers the port + the Gemini HTTP adapter behind it; the user provisions the key (generated from AI Studio under their Google account). The entire deterministic spine + all gate tests run without it via a stubbed proposer.

### 4.2 Novelty signature (§7) [beta-depth, dormant at launch]
Weights spec-locked (§174: exercise-set .40 / rep-zone .25 / techniques .20 / pattern .10 / order .05). **Inert at beta launch** (needs 2 prior same-day_role sessions to compare against). Beta: a simple feature-vector representation over the non-anchor layer + a weighted-distance function for the ≥30% soft-check (relax before feasibility). Richness is post-beta — it can't fire until data accrues.

### 4.3 Weak-point response (§9 L1→L2→L3) [beta-depth, dormant at launch]
**Dormant until ≥3 PROGRESS sessions.** The hook exists (Fork 3 soft-presents the `detect_stall` signal + limiter via `select_progress_window`). Beta: the model does the **L1 (mildest) response** (bias an accessory toward the identified limiter). The graduated escalation (don't-skip-levels, L1→L2→L3 across repeated stalls) needs stall *history* → post-beta.

### 4.4 Logging / thin-client surfacing [beta-depth, mechanical]
Logging per 7d (full provenance, replayable). Thin-client: the **minimal approve/regenerate surface** (show proposed session + rationale; approve or regenerate; first meso shows every session, later only surfaced not-clean ones). No edit (7e).

## 5. Beta-critical flags (must be right at launch)

1. **Cold-start is the COMMON path week one.** Every `day_role` is cold at first (freshly seeded library, nothing logged), so the Fork-4c **skeleton-fill is the common path until each day_role has one logged session**, not a rare edge. Its deterministic tie-break must produce a **trainable** session (a sensible per-pattern default, not merely the lowest-`movement_id` pick). Bar = *trainable, not optimal* — it's the fallback, the model is the primary path, and it goes dormant once last-valid-refreshed takes over. Don't over-invest in cleverness; do ensure the default isn't something you'd refuse to train.
2. **Analysis idempotency must be CORRECT (Fork 5d).** `run_analysis` keyed by `session_id`, no-op on re-log. A duplicate `e1rmhistory` row silently corrupts the stall/calibration signal (silent-wrong-data class) — this is the one idempotency guard that must be built correctly at beta, not deferred.
3. **Commit-at-approve makes regenerates write-free (Fork 7c).** No `current_load` write until approve ⇒ discarded regenerates touch nothing ⇒ generation idempotency is free. Verify the assembler computes-but-doesn't-write and the approval path is the sole `current_load` writer.
4. **The two-writer boundary holds (Fork 5c).** `run_analysis` writes outcome fields only; generation writes `current_load` only; disjoint fields, disjoint times. A test must assert neither crosses.

## 6. Data contracts

**Selections (LLM output — the only thing the model emits).** This is the `response_json_schema` passed to Gemini structured output (Fork 1 strengthening — the model's output is constrained to this shape at the API layer). Expressed in the Gemini structured-output dialect (OpenAPI-3.0 subset; the plan pins exact dialect details such as `nullable` vs type-union):

```json
{
  "type": "object",
  "properties": {
    "ordering": {
      "type": "array",
      "items": { "type": "string" },
      "description": "slot_ids in the session order chosen by the model"
    },
    "slots": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "slot_id":        { "type": "string" },
          "movement_id":    { "type": "integer" },
          "variant":        { "type": "string", "nullable": true },
          "technique_tags": { "type": "array", "items": { "type": "string" } }
        },
        "required": ["slot_id", "movement_id"]
      }
    },
    "rationale": { "type": "string" }
  },
  "required": ["ordering", "slots", "rationale"]
}
```

**No numeric prescription fields exist in this schema** — Fork 1 by construction, now enforced at the API layer, not just by prompt. The only integer is `movement_id` (a reference, not a prescription); the schema constrains *shape*, while **menu-membership** (`movement_id` ∈ the slot's candidate menu) and all structural/feasibility rules remain deterministic post-checks (Fork 3 menu + Fork 6 assemble + validate). A hallucinated off-menu `movement_id` is caught as a structural reject → repair (Fork 4).

**Context payload (engine → prompt, injected — Fork 2):** resolved skeleton (placed anchors + adaptive slot definitions); **per-slot the program's prescribed movement as the prior/default (§3A)**; per-slot candidate menus = program-anchor + feasibility/tier/pattern-filtered alternatives (Fork 3); owed-requirement flags; recent signatures (last 2 same-day_role); weak-point hint (`detect_stall` + limiter); open notes. (Built and injected only when the conditional-invocation gate fires — §3A; otherwise the program is emitted deterministically with no payload and no call.)

**Assembled Session (deterministic output — Fork 6):** existing `Session`/`PlannedSet` structures, all numbers computed; `current_load` values computed but written only at approve (7c).

## 7. Test / validation strategy (the gate)

The deterministic spine is fully testable by **stubbing the proposer port with fixed selections** (the LLM's nondeterminism is bounded by the spine, so the spine is what the gate covers). Required invariant tests:

1. **Selections-only by construction** — the selections schema has no numeric fields.
2. **Assembler determinism** — fixed selections → fixed Session numbers (same input ⇒ same output).
3. **Menu hard-filters feasibility** — no infeasible/wrong-tier/wrong-pattern movement is ever offered for a slot.
4. **Validator** — rejects each structural/requirement breach with an outcome-only reason; clamps a computed number over a cap.
5. **Repair bounded** — 3 retries → fallback; whole-session re-proposal carries the rejection context.
6. **Two-tier fallback always valid** — last-valid-refreshed path; **cold-start fallback emits the program as written** (a real designed session — valid + trainable by construction, §3A) (flag §5.1).
7. **Analysis idempotency** — re-logging a `session_id` does **not** append a duplicate `e1rmhistory` row or double-advance counters (flag §5.2).
8. **Commit-at-approve** — assemble does **not** write `current_load`; approve does; a regenerate-before-approve writes nothing (flag §5.3).
9. **Two-writer boundary** — `run_analysis` writes only outcome fields; generation writes only `current_load` (flag §5.4).
10. **Knee-frequency satisfiability** — owed-requirement flags + menu + validator can produce a session meeting docs/06 §4 frequencies (carried from the library gate).
11. **Conditional invocation (§3A)** — a quiet week (no slot carries a feedback/novelty/weak-point signal) emits the program deterministically with **no LLM call**; a week where ≥1 slot carries a signal **calls the LLM once** (whole-session). Meso 1 is provably deterministic.

Tests run on myflix: `ssh myflix 'cd ~/projects/IronLog-V2 && .venv/bin/pytest -q'`. No `from __future__ import annotations`.

Generation is unaffected by which rule advances the state.
- Graduated weak-point L2/L3 escalation (needs stall history).
- Novelty signature richness (needs accumulated sessions).
- Local-Qwen proposer swap (privacy/cost optimization once the loop is validated).
- In-session editing (requires solving human-adjust-without-breaking-determinism).
