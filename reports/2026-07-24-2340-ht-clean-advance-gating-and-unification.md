### Issues & Decisions
- **codex repeatedly under-delivered on multi-file specs within a single dispatch** (4 dispatches total, all partial on first attempt) — the retry-budget/provider-escalation rule (codex → codex once more if provider-specific, else gemini) worked as designed each time; gemini completed every hand-off fully. No design flaw found, just a real observed pattern worth remembering for future spec sizing/dispatch expectations on this kind of multi-file wiring task.
- **The backfill script's second bug was a genuine coverage gap**, not a review miss: Opus's review scope was explicitly "review, don't execute" (per spec, Tier A runs the script separately) — the ambiguous-join bug only exists at actual query-execution time, and neither the test suite nor the review caught it because the script was never actually run before tonight's deploy. Lesson for future one-off scripts: "syntactically correct and importable" (the spec's own bar) is not the same as "executes correctly against real data" — a scratch-DB dry run before the real deploy run is the right practice going forward (which is what caught this bug before it hit production).
- **Manual migration-apply + service-restart sequencing gap**: applying migrations directly via `sqlite3` (bypassing `ironlog/migrate.py`'s own `apply_pending`) left the `schema_migrations` tracking table unaware, causing the service's own `ExecStartPre` migration runner to fail on restart. Resolved by manually inserting the corresponding rows into `schema_migrations`. Better practice for next time: prefer running `python -m ironlog.migrate` itself (or an equivalent that updates the tracking table atomically) over raw `sqlite3 < migration.sql`, to avoid this class of drift entirely.
